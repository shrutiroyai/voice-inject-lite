I Fine-Tuned a 1.5B Model on My Laptop.
Here's When It's Worth It.

There's a lot of discourse about "just prompt better" vs fine-tuning. I did both. Here's what actually moved the needle for a local voice transcription system — and what didn't.

Context

The Problem I Was Solving

I built a fully local voice-to-text system that runs on Apple Silicon. You double-tap a key, speak, and cleaned-up text appears wherever your cursor is. The "cleanup" step is where the LLM lives — it fixes grammar, resolves self-corrections, and preserves your tone.

The system had two LLMs doing two jobs:

Dictation Cleanup (Qwen 1.5B)

Fix grammar, remove "um" and "uh", resolve self-corrections ("use Redis, no wait, Memcached" → keep only Memcached).

Instruction Rewrite (Phi 3.5B)

Select text, speak a command ("make this casual", "bullet points"), and the text is rewritten according to the instruction.

I wanted to collapse these into a single fine-tuned 1.5B model that handles both. Less RAM, faster loads, one model to maintain. The question was: can a small model learn both behaviors well enough to replace a model 2.5x its size?

What Worked

Fine-Tuning Taught the Model Things Prompting Couldn't

Here's the thing people miss in the "just prompt better" discourse: prompting controls what a model should do, but fine-tuning teaches it how. Some behaviors can't be prompted into a base model.

Self-Correction Resolution

When someone says "the meeting is at 3, no sorry, 4 pm" — the model needs to output only "The meeting is at 4 pm." This requires understanding that "no sorry" signals a correction, and that everything before it should be dropped.

The base model, regardless of prompt, would output both versions:

Base Qwen (any prompt):
IN:  "use Redis, no actually wait, let's use Memcached, it's simpler"
OUT: "use Redis. Wait, no, let's use Memcached. Its simpler"   // keeps both!

Fine-tuned:
IN:  "use Redis, no actually wait, let's use Memcached, it's simpler"
OUT: "I think we should use Memcached. It's simpler."          // resolves correctly

No amount of prompting fixed this. The model needed to see the pattern dozens of times to learn it.

"I think" Preservation

The base model treated "I think" as filler and removed it. But "I think we should ship this" is meaningfully different from "we should ship this" — the first is an opinion, the second is a directive. Fine-tuning with explicit examples where "I think" survives in the output taught the model to distinguish hedging-as-content from actual filler.

Tone Preservation

Base models tend to formalize. "yeah so basically the thing crashed" becomes "The application experienced a failure." Fine-tuning on examples that preserve casual tone ("Yeah, so basically the thing crashed") taught the model that casual speech should stay casual.

What Didn't Work

Where Fine-Tuning Hit a Wall

Fine-tuning doesn't give a small model capabilities it fundamentally lacks. Here's where I hit the limits:

Semantic Restructuring

When asked to "create bullet points" from a paragraph with complex reasoning, the 1.5B model either:

Over-compressed

Dropped 70% of the content, extracting only "action items" while losing all the reasoning and context that made them make sense.

Hallucinated

Invented explanations that weren't in the source text. Added "Reasoning:" sections with plausible-sounding but fabricated justifications.

The workaround was simple: replace "create bullet points" with "format each sentence as a separate bullet point." The model can format perfectly — it just can't reason about what constitutes a "point." That's a capacity issue, not a training issue.

The LoRA Configuration Trap

My first three training runs produced models identical to the base. Loss decreased during training, but outputs didn't change. The problem: my LoRA config was too conservative.

Config Didn't Work Worked
Rank 8 16
Target keys Q, V (2 projections) Q, K, V, O, gate, down (6 projections)
Layers 8 of 28 16 of 28
Trainable params 0.02% (311K) 0.5% (7.8M)
Learning rate 1e-5 5e-5
Final loss 2.9 (no behavior change) 0.3 (clear behavior change)

The lesson: for a 4-bit quantized 1.5B model with only 88 examples, you need to be aggressive. Conservative LoRA configs that work for 7B+ models with thousands of examples simply don't move the needle on smaller models.

The Key Insight

Training Examples Define Behavior More Than Prompts

This was my biggest takeaway: the model learns from the shape of your examples, not from what the system prompt says.

When my training examples showed compressed outputs (even with a prompt saying "don't compress"), the model learned to compress everything. When I had examples that removed "I think" in the context of confidence-rewriting, the model started removing "I think" in plain dictation too.

The fix was tedious but essential: I had to audit every training example and ask "is this output teaching the behavior I want in ALL contexts, or just this one?" Examples are implicitly teaching a policy, not just answering a question.

The rule I landed on

For dictation cleanup, the output should be nearly the same length as the input. The only things that make it shorter: removing filler words (um, uh) and resolving self-corrections (dropping the corrected-away part). Everything else stays. If you can't explain why a word was removed, it shouldn't be removed.

Verdict

When to Fine-Tune vs. When to Prompt

✓ Fine-tune when...

  • You need a specific behavior pattern the base model can't learn from instructions alone (self-correction resolution)
  • You want to replace a larger model with a smaller one for latency/resource reasons
  • The task is narrow and well-defined with clear right/wrong outputs
  • You need consistent tone or style that the base model keeps drifting from
  • You're running locally and every MB of RAM matters

✗ Don't fine-tune when...

  • The task requires reasoning beyond the model's parameter count (semantic restructuring on 1.5B)
  • A good prompt already gets you 90%+ of the way there
  • Your training examples would implicitly teach conflicting behaviors
  • You need the model to generalize to unseen instruction types
  • The effort of curating training data exceeds the value of the improvement

The discourse around "fine-tuning is dead, just prompt" misses something important: they solve different problems. Prompting is good at directing a capable model. Fine-tuning is good at installing a behavior pattern that the model doesn't have. For local, resource-constrained use cases where you need a small model to punch above its weight on a specific task — fine-tuning still has a place.

Recipe

How to Reproduce This

# Clone the repo
git clone https://github.com/shrutiroyai/voice-inject-lite.git
cd voice-inject-lite

# Look at the training data
cat finetune/train.jsonl | head -5

# Run the fine-tune (3 min on M-series Mac)
.venv/bin/python3 finetune/finetune.py

# Validate
.venv/bin/python3 finetune/validate.py
.venv/bin/python3 finetune/validate.py --base  # compare to base model

The setup

Base model: Qwen 2.5-1.5B-Instruct-4bit
Method: LoRA (rank 16, scale 0.125, dropout 0.05)
Targets: Q/K/V/O attention + gate/down MLP (6 of 7 projection types)
Layers: 16 of 28
Training: 88 examples, 600 iterations, batch 1, LR 5e-5
Hardware: Any Apple Silicon Mac (M1+), ~2.7GB peak memory
Time: ~3 minutes
Fine-tuned model: shruroy/Qwen2.5-1.5B-voice-inject
